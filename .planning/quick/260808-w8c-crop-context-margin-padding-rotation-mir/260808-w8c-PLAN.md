**D-w8c-01 -- crop context-margin is ONE shared, model-free function, `expand_box_with_margin(box,
margin_frac, image_w, image_h) -> BBox`, in `owlv2_oneshot.py`, used by BOTH the inference-time query
crop (`search()`) and (opt-in) the training-time crop-context anchor (`finetune_owlv2.py`).** Not two
independent implementations. This is the same fidelity guarantee D-dla-04 gave query-patch selection:
literal code reuse closes off the single largest correctness risk of this lever -- a margin computed
one way at training and another way at inference. `margin_frac <= 0.0` returns `box` unchanged
(byte-identical, no allocation); otherwise the box grows by `margin_frac * box.w` / `margin_frac *
box.h` on each side, clamped into `[0, image_w] x [0, image_h]` inline (never via `BBox.clipped_to`,
which raises on a fully-off-image box -- an input this function's callers never produce, since they
only ever expand an already-valid, already-in-bounds box).

**D-w8c-02 -- `Owlv2OneshotConfig.crop_context_margin_frac` and `FinetuneConfig.supcon_crop_margin_frac`
are SEPARATE fields, both defaulting to 0.0.** Mirrors D-dla-05's "pinned equal to the inference
default, not hard-coded" pattern one level further: the training field is not read unless
`supcon_crop_context` is also set, and its default keeps a `--supcon-crop-context` run's crop-context
anchor exactly as tight as it is today unless a human explicitly widens it to match a margin the
inference config will also use for evaluation.

**D-w8c-03 -- the margin sweep runs INFERENCE-ONLY against the ALREADY-EXPORTED `contrastive-crop`
ONNX (zero retraining), via a small, additive, backward-compatible extension to
`object_search.eval.tuning`.** `tune_method` already accepts a `grid` override; `run_domain_tuning` and
`_tune_methods_at_count` gain a new optional `grids: Mapping[str, Sequence[dict[str, object]]] | None
= None` parameter that, when given, overrides `_TUNING_GRIDS.get(method)` for that method only.
`None` (every existing call site, unchanged) reproduces today's exact behavior -- verified_fact 4's
blast-radius concern is the reason this must be additive-only and separately regression-tested, not
folded into a bespoke sweep script that reimplements tune-then-freeze-then-report.

**D-w8c-04 -- the margin sweep crosses `crop_context_margin_frac` with owlv2-oneshot's EXISTING tuning
grid (`max_box_area_frac` x `query_iou_frac`), not a margin-only grid.** The sweep script builds, per
margin value, a grid of `{**g, "crop_context_margin_frac": margin}` over every entry already in
`_TUNING_GRIDS["owlv2-oneshot"]`, so each margin is measured through the SAME tune-on-val/freeze/
report-on-test methodology every other arm's numbers came from, and the margin=0.0 cell is expected to
reproduce 260808-dla's already-committed `contrastive-crop` tuned F1 numbers exactly -- the sweep's own
built-in regression check on the new `grids` plumbing (verified_fact 3).

**D-w8c-05 -- the margin verdict is a data-driven, explicitly-stated gate, and the plan proceeds to
lever (B) regardless of its outcome.** `margin-verdict.md` records the four margins' tuned F1 for both
classes and states in one line whether any nonzero margin beats 0.0 on BOTH classes (a split
verdict -- helps one, hurts the other -- is stated as such, not rounded to a winner), and if so which
single value is carried into `--supcon-crop-margin-frac` for the final GPU arm. If no margin wins,
the final arm trains and evaluates at margin 0.0 and tests lever (B) alone.

**D-w8c-06 -- `--supcon-crop-augment` is layered ONLY on `--supcon-crop-context` and is a no-op
(ignored, logged) when crop-context is off.** It adds exactly ONE additional same-class SupCon
positive per training image per micro-batch pass -- not a rotation bank -- reusing D-dla-01's "ordinary
same-class positive, zero loss-math changes" rule and D-dla-04's "same selection function" rule for the
augmented view's query-patch pick.

**D-w8c-07 -- the augmentation choice is drawn from the SAME seeded `rng` used for crop-context box
selection, but ONLY AFTER `_crop_context_rows`'s existing per-image box-selection loop has consumed its

`--supcon-crop-augment`-off run's rng stream (and therefore its crop-context box selection and

**D-w8c-08 -- augmentation is applied to the RAW crop pixels (before `owlv2_preprocess_tensor`), on the

**D-w8c-09 -- the augmented anchor does NOT feed `crop_scene_agreement`'s diagnostic pool.** D-dla-06's

**D-w8c-10 -- the final GPU arm is trained ONCE, named `contrastive-crop-v2`, combining
