<task type="auto">
  <name>Task 2: rating.js + payload.js — the tiered widget and the null discipline</name>
  <files>frontend/js/rating.js, frontend/js/payload.js, frontend/index.html, frontend/css/app.css</files>
  <action>
The widget, tiered:
  - Tier 0: thumbs up / down — required, one click.
  - Tier 1: wrong matches, in **two mutually exclusive modes** — per-match verdicts (click the
    wrong boxes on the overlay) OR a bare `wrong_count` input. Choosing one visibly disables
    the other.
  - Tier 2: `missed_count` input.
  - An explicit **unratable / skip** control.
  - A free-text note.
  - **No 1–5 star scale.**

**UI-08, the highest-risk requirement:**
  - Count inputs render `value=""` (empty), never `0`.
  - One-click **"all correct"** and **"none missed"** buttons that write an explicit `0`.
  - Per-match verdicts start unmarked; `FP` stays unassessed until an explicit **"Confirm
    verdicts"** action sets a `verdicts_confirmed` flag.
  - The **EVAL-16 convention text** ("two boxes on one instance = 1 TP + 1 FP") is shown next
    to the widget.

`payload.js` — `buildRatingPayload(state) -> body`. An untouched count field becomes **`null`**,
not `0`. **No `|| 0` and no `?? 0` anywhere in this file** — that one character destroys the
null/zero distinction and makes every unreviewed run claim perfect precision and recall.
`verdicts_confirmed` is only true after the explicit confirm.

Because this is JS with no test runner, keep `buildRatingPayload` a pure function and prove it
via the Python side: `tests/test_rating_contract.py` POSTs the exact bodies this function
produces (a bare thumbs-up; a confirmed-verdicts body; an all-correct body with explicit 0) to
the real `/ratings` endpoint and asserts the stored/aggregated result matches — closing the
loop the JS cannot test alone.
  </action>
  <verify>pixi run test tests/test_rating_contract.py -v</verify>
  <acceptance_criteria>
    - grep of frontend/js/payload.js finds no '|| 0' and no '?? 0'
    - count inputs are created with value="" not "0"
    - "all correct"/"none missed" buttons write an explicit 0
    - verdicts_confirmed is false until the explicit confirm
    - per-match and bare-count modes are mutually exclusive (one disables the other)
    - the EVAL-16 convention text is present in the DOM
  </acceptance_criteria>
  <done>The rating widget preserves null-vs-zero end to end.</done>
</task>

<task type="auto">
  <name>Task 3: stats.js — the dashboard</name>
  <files>frontend/js/stats.js, frontend/index.html, frontend/css/app.css</files>
  <action>
Render `GET /stats` per method with plain SVG (no charting dependency):
  - thumbs-up rate with its **Wilson interval and n rendered inline**, the interval's meaning
    labelled. **Rank methods by the Wilson lower bound, not the raw rate** — that is what makes
    EVAL-14 operative (1/1 ranks below 50/100).
  - **`n = 0` renders distinctly** from a genuine wide interval (e.g. "no ratings yet", not a
    bar spanning 0–1) — [0,1] means "no information", the EVAL-17 distinction one layer up.
  - precision and recall each with their **own separate n**.
  - abstention count, error count, latency percentiles (preprocess/inference/postprocess split).
  </action>
