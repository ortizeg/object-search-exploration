Port the sibling design. Do NOT import from `basketball_2d_to_3d` — copy and adapt.

**The one change from the sibling:** the sibling's `BaseInferencer.predict` returns
`list[Detection]`. Here, inferencers return dense token grids, keypoint sets, and mask
protos, so make it generic: `BaseInferencer(ABC, Generic[OutT])` with
`predict(self, image: npt.NDArray[np.uint8]) -> OutT`.

`PostProcessor(Protocol[OutT])` — `__call__(self, outputs: list[npt.NDArray[Any]], orig_w: int, orig_h: int) -> OutT`.
The post-processor strategy is the second half of the ported design: it keeps model-specific
output decoding out of the session-management code.

`ONNXInputSpec` — a **frozen Pydantic model** that IS the preprocessing contract:
  `input_name: str | None = None`   # None = take the model's first input
  `dtype: str = "tensor(float)"`
  `shape: tuple[int | str, ...]`    # str elements are dynamic dims, skipped in validation
  `layout: Literal["NCHW", "NHWC"] = "NCHW"`
  `color_order: Literal["RGB", "BGR"] = "RGB"`
  `scale: float = 1.0 / 255.0`
  `mean: tuple[float, float, float]`
  `std: tuple[float, float, float]`
  `resize: Literal["stretch", "letterbox", "snap-to-multiple"] = "stretch"`
  `size_multiple: int | None = None`  # patch-based models: DINOv2 needs multiples of 14
  `interpolation: Literal["bilinear", "bicubic"] = "bilinear"`

  **`snap-to-multiple` is required, and it snaps rather than pads.** Research
  (`.planning/research/MODELS.md`) verified that DINOv2 silently **drops trailing pixels** when
  H or W is not a multiple of 14 — a 225 px side yields 16 patches, i.e. 224 px of content —
  which produces a systematic spatial offset in Method 3's similarity map rather than an error.
  So the policy resizes each side to the nearest multiple of `size_multiple` and records the
  exact scale factors used, which the caller needs to map token coordinates back to image
  pixels. Return those factors from `preprocess` (or expose them on a small
  `PreprocessInfo` result) — a method cannot correctly place a box without them.
  DINOv2 also wants `interpolation="bicubic"` and must **not** be centre-cropped (HF's default
  preprocessor would).
Making the contract a typed object rather than prose is what makes the
"pre/post-processing must be explicitly documented" constraint structurally enforced instead
of aspirational — you cannot construct an inferencer without stating every one of these.

`ONNXInferencer(BaseInferencer[OutT])`:
  `__init__(self, model_path, post_processor, input_spec, providers=None)`
  1. Raise `FileNotFoundError` if the model file is absent.
  2. Create the `ort.InferenceSession`.
  3. Read `session.get_inputs()[0]` (or the named input from the spec).
  4. **Init-time dtype validation (INFRA-09)** — if the model's declared type differs from
     `spec.dtype`, raise `ONNXContractError` naming both, including the numpy equivalents.
  5. **Init-time shape validation (INFRA-09)** — rank mismatch raises; per-dimension
     mismatch on non-dynamic dims raises with every mismatching index listed, not just the
     first. Skip a dimension when either side is a string (dynamic).
  6. Log the resolved input name, dtype, shape, output names, and providers at INFO.

  **Validate the INPUT contract only. Do not validate output shapes.** All three models this
  project will use declare **symbolic** output dimensions (DINOv2's token count varies with
  input resolution; SuperPoint's keypoint count is genuinely variable; FastSAM's box count
  depends on resolution). Research explicitly flags that a validator demanding static output
  shapes would reject every working model. Record the expected output *names and rank* for
  documentation, and check names exist — never assert concrete output extents.

  SuperPoint's variable keypoint count is not an inconvenience to be padded away: METHOD-04c's
  low-keypoint guard reads the count directly, so a fixed top-K export would defeat the guard.
  Keep variable-length outputs variable.
  Expose `input_spec`, `output_names`, `model_sha256` (lazily computed, for EVAL-09
  provenance).
  `preprocess()` implements the spec faithfully: colour conversion per `color_order`, resize
  per `resize` policy (including `pad-to-multiple` honouring `size_multiple`), scale, then
  `(x - mean) / std`, then transpose per `layout`, then add the batch dim and cast float32.
  `predict()` = preprocess → `session.run` → post_processor.

  `ONNXContractError(ValueError)` — a named exception so callers can distinguish a contract
  violation from any other ValueError.

  Expose `intra_op_num_threads` / `inter_op_num_threads` as optional args (default: leave ORT's
  own default alone). **Do NOT describe thread pinning as a determinism measure.** Research
  measured ORT thread count, OpenCV thread count, BLAS thread count, and argmax tie order as all
  producing **bit-identical** output, and found `use_deterministic_compute` is a **no-op on the CPU
  execution provider**. A docstring claiming thread pinning buys reproducibility would be false.
  If the args are documented at all, document them as latency/CPU-contention controls.

  What the docstring SHOULD say about reproducibility, because these are the real threats:
  set/dict iteration order, NMS tie-breaking, config-hash key ordering, and library-version
  drift. The model SHA-256 exposed for EVAL-09 is the guard against the last of those.

The class docstring must carry the full pre/post-processing description in prose as well,
because the project constraint requires it in the docstring specifically.

  <name>Task 6: Synthetic image generator with exact ground truth</name>
  <files>src/object_search/synthetic/generator.py, src/object_search/synthetic/__init__.py</files>
  <action>
`SyntheticSpec` — frozen Pydantic model driving generation:
  `seed: int = 0`
  `width: int = 960`, `height: int = 640`
  `mode: Literal["lattice", "scatter"] = "lattice"`
  `shape: Literal["rect", "triangle", "circle", "plus", "chevron"] = "plus"`
  `n_instances: int = 12`            # lattice: rows*cols is derived to be >= this
  `instance_size: int = 56`
  `scale_jitter: float = 0.0`        # 0 = identical scale; 0.5 = ±50%
  `rotation_jitter_deg: float = 0.0`
  `position_jitter: float = 0.0`     # fraction of cell size, lattice mode only
  `n_distractors: int = 0`           # similar-but-different shape/colour
  `clutter: float = 0.0`             # 0..1 background texture strength
  `fg_color: tuple[int,int,int] = (40, 90, 220)`   # BGR
  `bg_color: tuple[int,int,int] = (235, 235, 235)`

`SyntheticImage` — frozen: `image` is excluded from the Pydantic model (ndarrays do not
belong in a frozen schema); return a small dataclass instead holding
`image: npt.NDArray[np.uint8]`, `boxes: tuple[BBox, ...]`, `spec: SyntheticSpec`,
`slice_metadata: SliceMetadata`.

`synthesize(spec: SyntheticSpec) -> SyntheticImage`:
  - Single `rng = np.random.default_rng(spec.seed)`. Every random draw comes from it, in a
    fixed order. No use of `random`, no unseeded numpy calls, no iteration over an unordered
    set — determinism is a hard requirement, and a same-seed byte-equality test enforces it.
  - Background: fill `bg_color`; if `clutter > 0` add seeded Gaussian noise plus a few
    random large low-contrast blobs scaled by `clutter`.
  - lattice mode: choose `cols = ceil(sqrt(n))`, `rows = ceil(n/cols)`, lay instances on the
    grid with margins, apply `position_jitter` as a fraction of cell size.
  - scatter mode: rejection-sample non-overlapping positions (cap attempts, and if the cap is
    hit, return fewer instances and record the real count — never loop forever).
  - Per instance apply `scale_jitter` and `rotation_jitter_deg`, draw the shape with cv2
    (filled, anti-aliased off — `cv2.LINE_8` — so output is deterministic across OpenCV
    builds).
  - **Ground-truth box is the axis-aligned bounding box of the actually-drawn rotated
    shape**, computed from the transformed vertices, NOT the nominal size. A rotated square
    has a larger AABB than its side length; using the nominal box would make ground truth
    quietly wrong and every downstream IoU slightly off.
  - Distractors are drawn but NOT added to `boxes`, and are a different shape (or a hue-shifted
    colour) so they are genuine false-positive bait.
  - `slice_metadata` is filled exactly: true instance count, observed scale min/max,
    rotation min/max, clutter level. This is the EVAL-10 "free for synthetic" case.
  - Return boxes sorted by (y, x) so ordering is deterministic.

Add `save(out: SyntheticImage, image_path: Path) -> Path` writing the PNG and a sidecar
`<stem>.gt.json` containing the boxes, the spec, and the slice metadata — so the ground truth
travels with the image.

Add a `DEMO_SPECS: Mapping[str, SyntheticSpec]` dict of named specs used to generate the
