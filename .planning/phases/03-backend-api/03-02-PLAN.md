`GET /methods` — returns `registry.method_schemas()`: name, description, version, and
`config_schema` (from `config_model.model_json_schema()`). **No method name is written in the
api package** (API-01) — the route is a loop over the registry.

`GET /images` — lists demo images (synthetic set, chipset, basketball) with width, height, and
**`has_ground_truth: bool`** (true for synthetic and chipset which ship sidecar GT, false for
ad-hoc uploads) so the eval layer and UI can tell objectively-scorable images apart.
`POST /images` — accepts an uploaded image (multipart), stores it under a runtime uploads dir,
returns its id with `has_ground_truth=false`.

<task type="auto">
  <name>Task 3: /search with provenance and structured errors</name>
  <files>src/object_search/api/routes_search.py, src/object_search/api/errors.py, src/object_search/api/schemas.py, tests/test_api_search.py</files>
  <action>
`POST /search` — body `{image_id, exemplar, method, config, exploration?}`. Resolves the method
from the registry (unknown → 404 with the known names), validates config against the method's
`config_model`, loads the image, times preprocess/inference/postprocess, calls the method,
captures `Provenance.capture()` (the 11-field version), persists a `RunRecord`, and returns the
`SearchResult` plus the new run id.

**API-08 structured errors:** wrap the method call in try/except. On a method exception, build a
`MethodError`, persist the run with `outcome='error'` and the error fields, and return a typed
error body (HTTP 200 with `outcome='error'`, or a 4xx/5xx with the typed body — pick one and be
consistent; the run is persisted either way). **Never a bare 500 stack trace.** A config that
fails validation is a 422 with the field errors.

Tests:
- POST a search with the `ncc` method against a chipset image; assert a `SearchResult` comes
  back, then `GET` the run from the store and assert provenance (git_sha, config_hash,
  cv2_version), the three latency fields, and the candidate scores are all present.
- Register a throwaway method that raises; POST to it; assert the response is a typed error
  (not a stack trace) and the run is persisted with outcome='error'.
- POST invalid config; assert 422.
  </action>
  <verify>pixi run test tests/test_api_search.py -v</verify>
  <acceptance_criteria>
    - a searched run is retrievable with provenance, latency breakdown, and candidate scores
    - a raising method yields a typed error and a persisted outcome='error' run
    - invalid config yields 422, not 500
  </acceptance_criteria>
  <done>Search persists everything the evaluation design needs, and errors are evidence.</done>
</task>

  <name>Task 4: /ratings and /stats</name>

  <action>
`POST /ratings` — validates against the run's `retrieved` via
`validate_rating_against_run` (EVAL-18: `0 <= wrong_count <= R`; per-match wins over a bare
count and the discrepancy is flagged, not reconciled). **The request model's count fields
default to None, and the route does NOT coerce** — a submitted body without the counts stores
NULL.

`GET /stats` — returns `stats.scoreboard(conn)`: per-method thumbs rate with its Wilson
interval and n, precision and recall each with their own n, latency percentiles, abstention
and error counts, and the threshold-sweep-eligible count.

Tests (Phase 3 success criteria 3, 4, 5, over HTTP):
- POST a rating with per-match verdicts (confirmed) + a missed_count; GET /stats and assert
  precision, recall, and expected-count are correct and that no derived metric was stored.
- **POST a bare thumbs-up (no counts) through the real TestClient; GET /stats and assert this
  run contributes to neither the precision n nor the recall n** — the null discipline end to
  end.
- GET /stats and assert every rate carries an `n` and a Wilson interval, and that a method with
  n=0 thumbs renders the interval as null/absent rather than [0,1].
- POST wrong_count > retrieved; assert 422 with the flag, not a silent clamp.
  </action>
