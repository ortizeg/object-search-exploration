<objective>
Complete the harness: a seeded exemplar sampler that runs every method at BOTH 1 exemplar (the
product's real one-box operating point) and 3 exemplars (the published-benchmark convention),
the full benchmark sweep across method × dataset × {1,3} × {val,test} reusing the metrics and
per-slice machinery proven in 11-01, the report table carrying the literature's own columns
(P/R/F1 + AP/AP50/AP75 + MAE/RMSE/NAE), and the survey doc that makes the dataset/metric/protocol
choices defensible.

This is the consuming layer. The converters, sidecars, manifests, metric functions, and the
single-path benchmark entry were built and proven in 11-01/11-02; this plan adds the sampler and
the two swept dimensions, then renders the numbers and documents the protocol.

D-01..D-11 refer to the numbered "## Locked Decisions" in `11-CONTEXT.md`.

Purpose: produce leaderboard-comparable, held-out numbers for all four methods on all four
datasets at both operating points, tuned on val and reported on test, and document why.
Output: `sampling.py`, the swept benchmark + Hydra config, `scripts/build_research_report.py`,
and `docs/eval/research-datasets.md` (DOC-07).
</objective>

  <name>Task 2: Ratify the k-exemplar execution path and the exemplar-scoring semantics</name>
  <decision>
    Lock HOW a method is run at more than one exemplar (the 3-exemplar path — EVAL-23, ROADMAP
    success criteria 3 & 4) and HOW the sampled exemplar boxes are scored, BEFORE the sweep bakes
    both into every reported 3-exemplar number. `SearchFn.__call__(image, exemplar, config)` takes
    exactly ONE `ExemplarBox` and no method knows how to consume three; leaving the k>1 path
    undefined would let each reported 3-exemplar cell mean something different. D-05 requires both 1
    and 3 exemplars — this ratifies the single mechanism the executor is about to build (do not
    invent another).
  </decision>
  <context>
    Two specifics being fixed:
    (a) **k-shot LATE FUSION in the eval layer; `SearchFn` UNCHANGED.** A new eval-layer runner
    `run_multi_exemplar(spec_fn, image, exemplars, config) -> SearchResult` calls `spec_fn` once per
    sampled exemplar, UNIONs the resulting matches AND sub-threshold candidates across the k runs,
    then dedupes overlapping detections with the existing `search/common/nms.py` (tie-break
    `(-score, y, x)`); each GT is still matched at most once at scoring (EVAL-16). The `SearchFn`
    Protocol and all four method files are NOT touched — methods stay self-contained and
    `@register_method` remains the only indirection (CLAUDE.md). The 1-exemplar run is the k=1
    special case of this SAME runner, so 1 and 3 exemplars share one code path.
    (b) **Exemplar scoring semantics.** The sampled exemplar boxes REMAIN in `gt.boxes` and are
    scored like any other instance (a correct method re-detects its own exemplar; the FSC-147 /
    FSCD count convention counts exemplars). This keeps the recall denominator (`len(gt.boxes)`)
    identical between the 1- and 3-exemplar runs, so their P/R/AP numbers are directly comparable.
  </context>
  <options>
    <option id="option-a">
      <name>Exemplar boxes stay in gt and are scored; k-shot late fusion in the eval layer (recommended)</name>
      <pros>The recall denominator (`len(gt.boxes)`) is identical across count=1 and count=3, so
        the 1-vs-3 numbers are comparable — the exact comparison D-05 exists to make; matches the
        FSC-147/FSCD count convention; `SearchFn` and every method file stay untouched; 1 and 3
        exemplars run through one code path (`run_multi_exemplar`).</pros>
      <cons>The eval layer must dedupe the union of overlapping detections across k runs (reuses
        `search/common/nms.py`) rather than trusting a single method call.</cons>
    </option>
    <option id="option-b">
      <name>Exclude the k sampled exemplar boxes from BOTH predictions and gt (rejected)</name>
      <pros>A method is never asked to re-find the box it was handed.</pros>
      <cons>The recall denominator differs between count=1 (drop 1 box) and count=3 (drop 3 boxes),
        so the 1-vs-3 numbers are no longer comparable; and it diverges from the FSC-147/FSCD count
        convention, which counts exemplars. Rejected for both reasons.</cons>
    </option>
  </options>
